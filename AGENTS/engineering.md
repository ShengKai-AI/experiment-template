# 工程模式

## 身份与目标

工程模式负责项目架构、代码、接口、工具、依赖、测试和调试。目标是在不破坏实验记录的前提下，使项目实现保持清晰、统一、可维护和可验证。

## 工作范围

- 设计或调整项目架构。
- 开发和修改 Framework Code。
- 开发和修改 Experiment Code。
- 实现实验配置与运行记录工具。
- 编写测试、执行调试和修复工程问题。
- 处理依赖、环境和代码入口问题。

## 工作要求

1. 修改前检查现有架构、相关入口、调用关系和测试。
2. 先说明问题、预期输入输出和修改范围，再实施结构性变更。
3. 优先修复根因，避免为单次实验加入无法复用的临时逻辑。
4. 共享逻辑放入 `src/framework/`；实验专用逻辑放入 `src/experiments/` 下对应目录。
5. 修改公共接口、配置格式或目录结构时，同步检查调用方、示例和工具。
6. 执行与改动风险相称的测试，并记录实际测试范围和结果。

## 模式边界

- 工程测试、冒烟测试和调试产物不得写成正式实验结果。
- 工程模式不得为了让测试通过而静默改变正式实验参数。
- 除非任务明确要求，不创建正式 Run，不修改已完成 Run 的实验结果。
- 如果工作进入实验计划、正式运行或结果解释阶段，应切换到实验模式。

## 工程更新文档

- 新增或移除顶层模块、调整核心架构或数据流、修改公共接口或配置格式、变更多个模块共同依赖的 Framework Code，或者进行需要迁移的改动时，视为一次较大工程迭代。
- 较大工程迭代开始前，使用 `AGENTS/templates/engineering-update.md` 创建 `docs/updates/<YYYYMMDD>-<变更名称>.md`。
- 文档应在修改前记录目标、变更前状态、计划范围和验证方式；完成后在同一文件中确认或修正实际变更、偏差、验证结果和最终 commit。
- 同一次迭代跨越多次对话或多个 commit 时，持续维护同一份文档，不得按对话次数重复创建。
- 单文件小修复、注释或格式调整、不影响接口的局部重构以及普通测试补充，不创建工程更新文档。
- 工程更新文档的状态使用 `planned`、`in_progress`、`completed`、`partially_completed` 或 `cancelled`。

## 交付内容

完成工程任务时，应说明：

- 修改了哪些代码和接口。
- 对架构和已有实验有什么影响。
- 执行了哪些测试以及结果如何。
- 仍存在哪些限制或工程风险。
